# Data model (P1-T08)

Status: final for the MVP (P1-T08, reviewed 2026-11-24). Later tasks may refine a field, but a change to a relationship or an invariant goes back to `docs/02-decisions.md` first. Money is an integer in piasters (EGP x 100). Dates are UTC.

Sources: MongoDB Manual (Embedded Data, Atomicity and Transactions, Data Modeling Best Practices, Unbounded Arrays), Mongoose docs (`enum`, `unique` is an index and not a validator).

## User (collection `users`)
| Field | Type | Rules |
|---|---|---|
| name | String | required, trimmed |
| email | String | required, **unique index**, lowercase, trimmed |
| phone | String | required, Egyptian mobile format (validated at the edge with Zod) |
| passwordHash | String | required, `select: false` so it is never returned by default |
| role | String enum | required, default `customer`, one of `admin`, `catalog_manager`, `order_operator`, `customer` |
| isActive | Boolean | default `true` (deactivate instead of delete) |
| passwordChangedAt | Date | used to reject tokens issued before a password change |
| passwordResetTokenHash | String | `select: false`; hash of the reset token (the plain token is only emailed); cleared after use |
| passwordResetExpires | Date | `select: false`; short lifetime from config; cleared after use |
| addresses | [Address] | embedded, max 10 (see below) |
| createdAt, updatedAt | Date | `timestamps: true` |

Indexes: `email` unique; `passwordResetTokenHash` sparse (the reset flow looks the user up by the hash).
Careful: a sparse index skips only documents where the field is **missing**; a `null` value is still indexed (MongoDB Manual, Sparse Indexes). So "cleared after use" means `$unset` (or `undefined` in Mongoose), never `null`.

Reset token storage: two fields on the user (at most one pending reset; a new request replaces the old one, so the old link stops working). Chosen over a separate collection because it is bounded to one, it is read together with the user, and it is never queried alone. Revisit only if multiple active tokens or an attempts history is needed.

Decision: **role is a single enum field** (see `docs/02-decisions.md`).

### Address (embedded in User)
Fields: `label`, `recipientName`, `phone`, `governorate`, `city`, `street`, `details`, `notes`, `isDefault`. Each has its own `_id`.
- Bounded (max 10, enforced in validation), always read with the user, never queried alone, ownership is implied by the parent.
- At most one address has `isDefault = true` (enforced in the service).
- `governorate` must be a known governorate because shipping zones match on it.
- An order keeps a **snapshot** of the address, not a reference (see Order).

Decision: **addresses are embedded** (see `docs/02-decisions.md`).

## AuditLog (collection `auditlogs`)
Append-only record of who changed what and when.
| Field | Type | Rules |
|---|---|---|
| actorId | ObjectId (ref User) | required |
| actorRole | String | role at the time of the action (it can change later) |
| action | String enum | for example `price_changed`, `stock_adjusted`, `role_changed`, `coupon_changed`, `order_status_changed` |
| entityType | String | for example `Variant`, `Order`, `Coupon`, `User` |
| entityId | ObjectId | required |
| before, after | Mixed | old and new values (only the changed fields) |
| reason | String enum | required for every stock change: `initial_stock`, `restock`, `damaged`, `lost`, `correction` (manual, P3-T05) and `order_placed`, `order_cancelled` (automatic, P5) |
| note | String | optional free text from staff |
| meta | Mixed | small extra context, for example `{ change: -2 }` or `{ orderId }` for stock changes caused by an order |
| createdAt | Date | automatic |

Indexes: `{ entityType, entityId, createdAt: -1 }` (history of one entity) and `{ actorId, createdAt: -1 }` (activity of one person).
Why its own collection: it is unbounded, it is queried alone, and it is never edited.

**The audit log is also the stock ledger.** There is no separate `InventoryAdjustment` collection: every stock change (manual or by an order) writes one AuditLog entry with `entityType: "Variant"`, `before.stock`, `after.stock`, `reason` and `meta.change`. The current stock lives only on the Variant; the log explains how it got there. Why: one place to read history, and the brief asks for an audit of inventory changes anyway. Revisit (a dedicated ledger collection) only if stock history needs its own reports.

`entityType` + `entityId` is a **polymorphic** reference (it can point to a Variant, an Order, a Coupon, a User, ...), so it is not a Mongoose `ref` and is never populated automatically. `actorRole` is a snapshot of the role at that moment.

## Product (collection `products`)
| Field | Type | Rules |
|---|---|---|
| title | String | required |
| slug | String | required, unique, generated by the server |
| description | String | |
| categoryId | ObjectId (ref Category) | required, indexed (filter by category) |
| images | [String] | URLs, maximum count enforced in validation (embedded: bounded, always read with the product) |
| isActive | Boolean | default `true` |

Indexes: `slug` unique; `categoryId`; a text index for search (decided in P3-T07).
A product does not store its variants. Variants point to the product.

## Variant (collection `variants`, one document per SKU)
| Field | Type | Rules |
|---|---|---|
| productId | ObjectId (ref Product) | required |
| sku | String | required, **unique index**, trimmed and uppercase |
| size, color | String | normalized to lowercase |
| price | Number | integer in piasters, `> 0` (a sellable SKU with price 0 is almost always a typing mistake) |
| stock | Number | integer, `min: 0`, default `0` (changed only by inventory adjustments and orders) |
| initialStockSet | Boolean | default `false`; makes the "one initial_stock only" rule atomic (proposal, final decision in P3-T05) |
| isActive | Boolean | default `true` |

Indexes: `sku` unique; `{ productId, size, color }` **unique** (no two variants of one product with the same size and color). This compound index also serves "all variants of a product" (`productId` is its prefix), so no separate `productId` index is needed. A missing `size` or `color` is indexed as `null`, so a product can have only one variant without a size (MongoDB Manual, Unique Indexes): that is the rule we want.

**Purchasable** (used by cart, quote and order): `variant.isActive` **and** its `product.isActive` **and** the product's `category.isActive`. Deactivating a product or category does not touch its variants; the check reads all three. Never copy `isActive` down to the variants, or two flags can disagree.

Why a separate collection (full reasons go to `docs/02-decisions.md`):
- A unique index on an array field only prevents duplicates **between different documents**, not inside one document (MongoDB manual, Unique Indexes). Embedded variants could not enforce "unique SKU and unique size+color inside one product" in the database.
- Reducing stock is one conditional update on one document (`stock >= n`), which is atomic.
- The cart, order items, inventory adjustments and audit log all point to one `variantId`.
- Cost: the product list needs price range and in-stock info, so it uses an aggregation (or denormalized fields later, decided in P3-T06). Creating a product with variants writes to two collections, so it uses a transaction.

## ShippingZone (collection `shippingzones`)
| Field | Type | Rules |
|---|---|---|
| name | String | required, unique |
| governorates | [String] | non-empty, values from the shared governorate constant |
| fee | Number | integer in piasters, `>= 0` |
| isActive | Boolean | default `true` |

Invariant: a governorate belongs to at most one **active** zone. Planned guarantee: a **unique partial index** on `governorates` with `partialFilterExpression: { isActive: true }`. Documented facts: a unique index applies across documents, and in a partial unique index the constraint applies only to documents that match the filter. The combination (multikey + unique + partial) is our inference and must be tested on Atlas in P4-T01.
A governorate in no active zone means no delivery there. Orders and quotes match the zone by the governorate string in the address (no foreign key).

## Coupon (collection `coupons`)
| Field | Type | Rules |
|---|---|---|
| code | String | required, **unique**, trimmed, uppercase |
| type | String enum | `percent` or `fixed` |
| value | Number | percent: integer 1 to 100; fixed: integer piasters > 0 |
| maxDiscount | Number | integer piasters, percent coupons only |
| minSubtotal | Number | integer piasters, default `0` |
| startsAt, expiresAt | Date | `expiresAt > startsAt` |
| usageLimit | Number or `null` | `null` means unlimited |
| usedCount | Number | default `0`, changed only by the server |
| isActive | Boolean | default `true` |

Usage counting: the quote only **reads** `usedCount < usageLimit` (a friendly check). The guarantee is one conditional atomic update when the order is created (filter: active, inside the dates, `usedCount < usageLimit`; update: `$inc usedCount`). Cancelling the order does `$inc -1` in the cancellation transaction. The order stores a **snapshot** of the coupon (see Order).

## Cart (collection `carts`)
| Field | Type | Rules |
|---|---|---|
| userId | ObjectId (ref User) | required, **unique** (one cart per user) |
| items | [{ variantId, quantity }] | embedded, maximum line count; quantity is an integer from 1 to a per-line maximum |

- **No price in the cart.** The cart is an intention, the price is read from the Variant when the cart is shown.
- Stale lines (inactive variant, stock too low, price changed) are computed when the cart is read, not stored.
- One line per variant is **not** guaranteed by an index (a unique index does not apply inside one document). The service uses a conditional update (add the line only if the variant is not in the cart, otherwise increase the quantity). Accepted trade-off: a duplicate line is harmless, unlike overselling.
- The cart is cleared inside the order-creation transaction.

## Order (collection `orders`)
An order is a closed financial event: it must explain itself years later, even if the product, the address or the coupon changed or disappeared.

| Field | Type | Rules |
|---|---|---|
| orderNumber | String | required, **unique**, human readable (for example `ORD-20261124-K7M2QX`); generation method decided in P5-T01 |
| userId | ObjectId (ref User) | required |
| items | [OrderItem] | embedded, non-empty, maximum count |
| shippingAddress | object | embedded **snapshot**: recipientName, phone, governorate, city, street, details, notes |
| subtotal, discount, shippingFee, total | Number | integers in piasters, `>= 0`; `discount <= subtotal` (the coupon applies to the subtotal only); `total = subtotal - discount + shippingFee` |
| currency | String | `EGP` |
| coupon | object or null | `{ couponId, code, type, value }` (couponId is a reference used to release usage on cancel; the rest is a snapshot) |
| status | String enum | `pending`, `accepted`, `packing`, `shipped`, `delivered`, `cancelled` |
| paymentMethod | String enum | `cod` only for now (extensible) |
| paymentStatus | String enum | values decided in P1-T09 |
| paidAt, paymentConfirmedBy | Date, ObjectId | set when COD payment is confirmed |
| statusHistory | [{ status, at, by, byRole, note }] | embedded, append-only, bounded by the state machine; `by` refs User, `byRole` is a snapshot (customer or staff) |
| shipment | object | `{ carrier, trackingNote, shippedAt, deliveredAt }` (no separate Shipment entity) |
| cancellation | object | `{ cancelledAt, cancelledBy, cancelledByRole, reason }` |
| createdAt, updatedAt | Date | automatic |

### OrderItem (embedded in Order)
`productId` and `variantId` (references: trace and restock), `sku`, `title`, `size`, `color`, `unitPrice`, `quantity`, `lineTotal` (snapshots).

Indexes: `orderNumber` unique; `{ userId, createdAt: -1 }` (customer history); `{ status, createdAt: -1 }` (staff queue).

Why items, statusHistory and shipment are embedded: bounded, always read with the order, snapshots, and a status change plus its history entry is one write on one document (atomic). That allows a conditional update such as "set `accepted` only if the status is still `pending`", so two staff members cannot both win.

Mongoose: mark snapshot fields `immutable: true` (documented: an immutable path cannot change after creation, and `updateOne` / `updateMany` strip updates to it by default).

## ReturnRequest (collection `returnrequests`, stretch phase)
| Field | Type | Rules |
|---|---|---|
| orderId | ObjectId (ref Order) | required |
| userId | ObjectId (ref User) | required |
| items | [{ variantId, sku, title, quantity }] | embedded; quantity not above what was bought |
| reason | String | required |
| status | String enum | `requested`, `approved`, `rejected`, `received` |
| refundStatus | String enum | `not_required`, `pending`, `refunded_manually`, **separate** from `status` |
| statusHistory | [{ status, at, by }] | embedded |

Indexes: `{ userId, createdAt: -1 }`, `{ status, createdAt: -1 }`. Option for "one open request per order": a unique **partial** index on `orderId` where `status` is in `[requested, approved]` (partial filters support `$in`); final choice in P7-T04.
Why its own collection: a different lifecycle (after delivery), queried alone by staff, and it must never overwrite the order or its payment history (brief section 06).

# Summary tables

## Snapshots on the Order (and why)
| Field | Reason |
|---|---|
| items: unitPrice, lineTotal | prices change; an old order keeps the price paid |
| items: title, sku, size, color | the product can be edited, deactivated or deleted |
| shippingAddress (all fields) | the user can edit or delete the saved address; we must know where it was sent |
| shippingFee | the zone fee can change |
| discount, coupon code / type / value | the coupon can be edited or deactivated |
| subtotal, total | computed from the prices of that moment (keeps "quote total = stored total") |

Kept as references on purpose (not snapshots): `userId` (owner), `items.variantId` (restock on cancel), `coupon.couponId` (release usage on cancel).
The cart is **not** a snapshot: it is an intention and always shows current prices.

## Invariants: where each one lives
**In the schema and indexes (the database is the last line of defence):**
- `users.email` unique; `variants.sku` unique; `variants { productId, size, color }` unique; `coupons.code` unique; `carts.userId` unique; `orders.orderNumber` unique.
- Active shipping zones never share a governorate: unique **partial** index (to be tested on Atlas in P4-T01).
- Enums: role, order status, payment method and status, coupon type, return status.
- Money fields are integers `>= 0` (variant price `> 0`); `variants.stock >= 0`; order item quantity is an integer `>= 1`; order items are non-empty.
- Snapshot fields are `immutable`.

**In services and transactions (rules a schema cannot express):**
- Stock deduction: one conditional atomic update per variant (`stock >= n`). Mongoose update validators are **off by default** (Mongoose docs, Validation), so the filter is the real guarantee, not `min: 0`.
- Order creation is one transaction: create the order, deduct stock, increase coupon `usedCount`, clear the cart.
- Coupon limit: conditional atomic update (`usedCount < usageLimit`); the quote only does a friendly read.
- Status transitions: conditional update on the current status plus a `statusHistory` entry.
- Ownership: the user id always comes from the verified token; foreign resources answer `404`.
- At least one active admin always exists; an admin cannot demote or deactivate themselves.
- One default address; maximum address count; one cart line per variant (conditional update).
- Totals are recomputed on the server; `expectedTotal` mismatch is rejected; `discount <= subtotal` so the total never goes negative.
- A line is purchasable only if variant, product and category are all active (checked in cart, quote and order).
- Every stock change writes one audit entry with a reason (the audit log is the stock ledger).
- `initial_stock` only once (the `initialStockSet` flag in the same atomic update), return window, return quantity not above what was bought.

## Scenario 01 on this model
> "Add 2 variants of a product with separate SKUs; buy one variant and verify only its stock changes."

1. Product "Sneaker" (one `products` document) with two `variants` documents: `SNK-42-BLK` and `SNK-43-WHT`, both with `stock: 0` at creation.
2. An inventory adjustment `initial_stock` sets `SNK-42-BLK` to 10 and `SNK-43-WHT` to 7 (one atomic update each, one audit entry each).
3. The customer adds `SNK-42-BLK` x1 to the cart (the cart stores only `variantId` and `quantity`).
4. Order creation, in one transaction: the order stores snapshots (sku, title, price, address); then **one** conditional update on the `SNK-42-BLK` document (`stock >= 1`, decrease by 1); the cart is cleared.
5. Result: `SNK-42-BLK` has 9; `SNK-43-WHT` is still 7 (its document was never touched); the Product document is unchanged.
